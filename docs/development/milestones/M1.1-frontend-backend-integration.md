# M1.1 — Frontend–Backend Local Integration

## Objective

Establish the first working local integration between the Angular frontend and the Spring Boot backend.
The Angular application calls the existing backend health endpoint and displays the backend status in the UI.

---

## Integration Architecture

```
Browser (localhost:4200)
  └─► Angular DevServer (ng serve)
        └─► Angular proxy (/api → http://localhost:8080)
              └─► Spring Boot (localhost:8080)
                    └─► GET /api/health
                          └─► HealthController → HealthService → HealthResponse JSON
```

All frontend HTTP calls use the relative path `/api/*`.
The Angular development proxy forwards those requests to `http://localhost:8080`.
No backend URL is hardcoded in Angular service code.
In production the frontend is served from the same origin as the backend, so `/api` resolves correctly without a proxy.

## Health Endpoint Contract

| Property | Value |
|---|---|
| Method | `GET` |
| Path | `/api/health` |
| Backend port | `8080` |
| Content-Type | `application/json` |

### Response JSON

```json
{
  "status": "UP",
  "application": "lease-demo",
  "version": "0.1.0"
}
```

| Field | Type | Description |
|---|---|---|
| `status` | `string` | Backend health status, always `"UP"` in this milestone |
| `application` | `string` | Application name |
| `version` | `string` | Application version from `application.yml` |

## Frontend Model

**File:** `frontend/src/app/core/models/health-response.model.ts`

```typescript
export interface HealthResponse {
  status: string;
  application: string;
  version: string;
}
```

Strictly typed to match the backend JSON contract.
No `any`, no `Record<string, any>`, no untyped literals.

---

## ApiService Responsibility

**File:** `frontend/src/app/core/services/api.service.ts`

- Generic, infrastructure-level HTTP abstraction.
- Wraps Angular `HttpClient` with a configurable base URL prefix (`environment.apiBaseUrl`).
- Provides typed `get<T>`, `post<T>`, `put<T>`, `patch<T>`, `delete<T>` helpers.
- No business logic. No health-specific code.

The base URL is configured via the environment file:

| Environment | `apiBaseUrl` |
|---|---|
| Development | `/api` (proxy forwards to `http://localhost:8080`) |
| Production | `/api` (served from same origin) |

---

## HealthService Responsibility

**File:** `frontend/src/app/core/services/health.service.ts`

- Feature service responsible for the health domain.
- Calls `ApiService.get<HealthResponse>('/health')`.
- Exposes `getHealth(): Observable<HealthResponse>`.
- No component-specific state, no DOM or UI logic.
- Registered as `providedIn: 'root'` singleton.

---

## Angular HttpClient Configuration

`HttpClient` is registered in `frontend/src/app/app.config.ts` using the modern standalone API:

```typescript
provideHttpClient(
  withInterceptors([loggingInterceptor, errorInterceptor])
)
```

Both functional interceptors remain active:

| Interceptor | File | Responsibility |
|---|---|---|
| `loggingInterceptor` | `core/interceptors/logging.interceptor.ts` | Logs request/response timing |
| `errorInterceptor` | `core/interceptors/error.interceptor.ts` | Normalises HTTP errors |

No `NgModules` were introduced.

## Angular Proxy Configuration

**File:** `frontend/proxy.conf.json`

```json
{
  "/api": {
    "target": "http://localhost:8080",
    "secure": false,
    "changeOrigin": true,
    "logLevel": "info"
  }
}
```

The proxy is wired into the Angular serve configuration in `angular.json`:

```json
"serve": {
  "options": {
    "proxyConfig": "proxy.conf.json"
  }
}
```

Active whenever `ng serve` or `npm start` is used.
No CORS configuration is required for local development because all requests go through the same origin proxy.

## Dashboard Component — Reactive State

**File:** `frontend/src/app/features/dashboard/dashboard-placeholder.component.ts`

The component models three explicit UI states using a discriminated union:

```typescript
type HealthViewState =
  | { status: 'loading' }
  | { status: 'success'; data: HealthResponse }
  | { status: 'error'; message: string };
```

State is managed with an Angular signal (`signal<HealthViewState>`).
The template uses `@if` blocks to render only the relevant state.
A **Retry** button is shown in the error state and calls `load()` which re-triggers the request.

### UI States

| State | Display |
|---|---|
| Loading | `Backend status: checking…` (grey) |
| Success | `Backend status: available` (green) + application details |
| Error | `Backend status: unavailable` (red) + error message + Retry button |

## Local Startup Order

1. Start the backend:
   ```bash
   cd backend
   mvn spring-boot:run
   ```
   Backend available at: `http://localhost:8080`

2. Start the frontend (in a separate terminal):
   ```bash
   cd frontend
   npm start
   ```
   Frontend available at: `http://localhost:4200`

3. Open `http://localhost:4200` — the dashboard displays the backend health status.

The Angular proxy routes `GET http://localhost:4200/api/health` → `GET http://localhost:8080/api/health`.

## Known Limitations

- CORS is not configured on the backend because local development uses the Angular proxy.
- The health endpoint always returns `"status": "UP"` in this milestone; real health checks (database, etc.) will be added in future milestones.
- No authentication is implemented.
- No exchange-rate functionality is implemented.
- The `subscribe()` call in the dashboard component is not managed with `takeUntilDestroyed` because the component is destroyed on navigation, preventing leaks for this use case; a `DestroyRef`-based cleanup will be added when more subscriptions are needed.
